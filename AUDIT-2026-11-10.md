## Findings, with how to implement each (for Opus 5.5)

### Usability and look

**U1 🟠 ASK — Ingredients far below the fold on a phone.** Opening a recipe on a 390 px phone shows, in order: the
photo (250 px), category, name, servings, source, the "Nutrition per 100 g / ✨ Calculate" box, "Scale ingredients"
×0.5…×6, "Make it for N servings", "Units: Metric / Imperial", the diet tag, Notes — and only then **Ingredients**, about
740 px down (measured on the walk; the screenshot `phone-en-view.png`). A cook at the stove scrolls past five controls
to reach the list. Proposal, for Tony to choose from:
  (a) Nutrition becomes one line, "Nutrition per 100 g ›", that opens the box on a tap (it is empty until Calculate).
  (b) Scaling and "Make it for" share one row: `×0.5 ×1 ×2 ×3 | − 4 +`.
  (c) Units move into that row's end, or under Ingredients' heading.
  (d) Notes go after Method (they are read after cooking, mostly), unless short.
  *How:* the recipe window is built in `openView` (index.html ≈ 22513) and the block builders after it (the nutrition
  box, the scale row — search "SCALE INGREDIENTS", "MAKE IT FOR", "NUTRITION PER 100G" in the markup); the order is
  markup order, so (d) is a move; (a) is a `<details>`-like toggle with the box hidden until opened (keep its id so
  `calcNutrition` finds it); (b)/(c) are CSS (`display:flex; flex-wrap:wrap`) on a phone only (`@media (max-width:
  600px)`), nothing on a computer. Self Test: on a 390 px viewport, the Ingredients heading's top must be under 480 px
  for a recipe with notes and a source (measure with `getBoundingClientRect`), and the computer layout unchanged
  (phone-fit.js style). Risk: low; a look Tony should approve first (mock-up by screenshot before committing).

### Security and privacy

**S1 🟠 ASK — Fetching with the public key alone.** `fetch-url` (any http(s) page, 60 KB of its text returned),
`facebook-fetch`, `instagram-fetch`, `fb-probe`, `video-from-url` / `video-recipe` (Google's Gemini allowance),
`photo-search` (the photo libraries' keys) and `photo-fetch` (up to 12 MB of any image's bytes, 600 a minute an
address) need the app key, which is in the page, and an allowed Origin — or no Origin at all, as any script has. The
only bounds are per-address minute limits and the daily ceilings. The October audit left this as "🟡 still open".
Since then the beta is by invitation only and every real user of these features is signed in (the AI already refuses
without a sign-in, v66). Proposal: these actions take `idToken` and refuse without a verified sign-in from one of the
served projects — a stranger then gets nothing from the server at all. "Continue offline" users lose website imports
(they already lose the AI step of every import). *How (Worker):* one helper, `signedCaller(body, env)` →
`verifyIdToken` (already written) with `email_verified`; call it at the top of each of the eight actions (lines ≈
1312–1446; `video-file` reads the header path at ≈ 1225); `health` stays open; add to `tests/worker-cors.mjs` a
refused call without a token and an accepted one with the test keys (`__testKeys`, see the mail tests for the token
builder). *How (app):* a `workerBodySigned(obj)` that adds `idToken: await _fbUser.getIdToken()` and `hid`, used at
the call sites (`action: 'fetch-url'` ≈ 27353 and 27615; photo-search/photo-fetch in `photoSearch*`/`fetchPhotoBlob`;
the video paths in `importRecipeVideo`/`videoFromUrl`); when signed out, say "Sign in first — importing from the web
needs it" before calling. Self Tests: `ai_calls_prove_who`-style check that each of these requests carries a token.
Risk: a signed-in user whose token is stale gets one refusal — `aiPrepare()` already refreshes; reuse it.

**S2 🟡 SAFE (done) — Security headers.** A `_headers` file at the root (copied into every build by `tools/build.js`)
makes the two Cloudflare Pages copies answer with `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors
'none'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`. The page's `<meta>`
policy cannot carry frame-ancestors (browsers ignore it there and say so in the console), so the clickjacking guard was
the page's own script alone; now the browser refuses the frame first. GitHub Pages (the family's copy) takes no
headers; its guard stays the script. Nothing here changes what the page may load. *Check after the deploy:* `curl -sI
https://tonys-recipes-test.pages.dev/ | grep -i frame`.

**S3 🟡 ASK — The relays.** `allorigins.win`, `corsproxy.io`, `codetabs.com` (index.html ≈ 27647) are still tried when
the server cannot fetch a page; they see the address and could alter the page (everything is escaped and nothing is
saved before "Add", so the harm is bounded). Carried from October. Proposal: remove them, or keep only for pages the
server reports as refusing it (403/429), never as a first fallback. *How:* `fetchPageText` (the function holding the
relay list): drop the relay step, say "The page could not be fetched — try pasting its text" instead; take the three
hosts out of the CSP's `connect-src`; Self Test `sec_no_relays`. Ask Tony whether any of his sources needs them.

**S4 🟡 note — `link-sent`.** The count of sign-in-link e-mails (Worker ≈ 3300) is taken on the app's word, behind the
key and the minute limit only; a stranger could inflate it and provoke a false "near the daily limit" alert to the
owner. No data at risk; left as is (the caller is not signed in yet by definition).

**S5 🟡 ASK — Actions pinned to tags.** `actions/checkout@v5`, `setup-node@v5`, `setup-java@v5`, `upload-artifact@v4`,
`configure-pages@v5`, `deploy-pages@v4` follow moving major tags. Pinning to commit SHAs (with the tag as a comment)
is the supply-chain norm; Dependabot's `github-actions` ecosystem keeps them current with monthly PRs. *How:*
`.github/dependabot.yml` with `package-ecosystem: github-actions`, `schedule: monthly`; then replace each `@vN` with
`@<sha> # vN` once. Asked because it adds PRs to the repository.

**S6 ✓ The rules, read whole.** No hole found. Noted: `recipes`, `photos`, `chats`, `state` accept any shape and size
from an editor (bounded by membership and Firestore's 1 MB a document); `deleteAsks`, `movedOn`/`recipeGone`, `talk`
(one-to-one messages readable by the two only), `recipeGifts` (unguessable ids, 4 weeks), `testerInvites`
(fingerprints), `feedback` (5 KB text, 750 KB screenshot) are as the comments say.

**S7 ✓ The server.** `verifyIdToken` checks signature, `aud` (served projects only), `iss`, `exp`, `iat`; owner
operations need a Google sign-in and the authenticator once switched on; every D1 statement binds its values; the
server writes no log lines with personal data; alerts go to the owner's address only; `invite-for` checks membership
with the caller's own token; invitation requests no longer reach the reports repository (v103).

**S8 ✓ The app's HTML.** The code added since October (links between recipes, the contents list, delete requests, the
invitation window, the owner's requests tab, the kitchen dictionary line) escapes with `escH`/`escA`/`jsA`; the filter
bar's `onclick="toggleCatFilter('…')"` takes only the fixed `CATS`/`DIETS` lists; help answers go through
`helpLineHtml` (text escaped, `**bold**` only). The CSP keeps `script-src 'unsafe-inline'` (inherent to the one-file
design, as the September audit said).

**S9 ✓ Privacy.** Statement 1.15 covers the request for someone else; the device log masks addresses; the Worker's
e-mail about a request names the person to the owner only; the extension asks for `activeTab`, `scripting`,
`contextMenus`, `storage` and nothing else; Firebase's web key restriction is verified (CLAUDE.md).

**C2 🟠 ASK — Structured recipe data is ignored.** Most recipe sites (and the big Israeli ones to a large degree)
embed their recipe as schema.org `Recipe` JSON-LD: name, ingredients, instructions (HowToStep), yield, times, image.
The server strips the page to text and the app sends up to 60,000 characters to Sonnet to find what the page already
states. Proposal: `fetch-url` also returns the Recipe objects it finds; when the page holds exactly one, the app builds
the recipe from it **without an AI call** (or with one Haiku call to tidy wording — Tony's choice), and the current
path stays for everything else. Saves about 90 % of such imports' cost and 10–30 s of waiting each; also more faithful
(the site's own ingredient list, no AI guessing). *How (Worker, `fetch-url` ≈ 1446):* before stripping, collect every
`<script type="application/ld+json">`, parse (arrays, `@graph`), keep objects whose `@type` is or includes `Recipe`;
normalise: `recipeIngredient[]`, `recipeInstructions` (strings, `HowToStep.text`, `HowToSection.itemListElement`),
`recipeYield`, `prepTime`/`cookTime`/`totalTime` (ISO 8601 durations → minutes), `image` (string, array or
ImageObject.url), `description`, `keywords`, `recipeCategory`, `recipeCuisine`; return `recipes: [...]` beside `text`.
Also read microdata (`itemprop`) only if cheap — JSON-LD covers most. *How (app):* in the URL import, if
`data.recipes.length === 1`, `recipeFromStructured(obj)` → the same object `extractRecipesFromText` returns, then the
usual preview (the person still sees and confirms); if more than one, hand them to the multi-recipe preview; else the
AI path as today. Keep `source`, the photo via `photo-fetch`. *Tests:* fixtures of three real pages' JSON-LD (one
Hebrew), a Worker test for each shape, a Self Test that the import of a fixture page makes no AI call
(`_aiCallUncached` stubbed to throw). Risk: low — the AI path remains; worth asking Tony which sites he imports from
most, to test with them.

**C3 🟡 ASK — Idea lists on Haiku.** `runExplore`, `runSuggest` (≈ 25463, 25579) and "What can I make" ask Sonnet for
lists of meal ideas with up to 3,000 answer tokens; Haiku 4.5 does lists of this kind well at a fifth of the price.
*How:* pass `AI_MODEL_SMALL` as the model argument; keep Sonnet for imports and translation (quality matters there);
update `ai_model_routing`'s expectations. Ask Tony to try a few Hebrew idea lists on the test copy first.

**C4 🟡 ASK — Diet tagging one recipe at a time.** `aiTagAllDiets` (≈ 39763) loops over every untagged recipe with one
Haiku call each (80 tokens out): 300 recipes = 300 calls, 300 round trips, minutes of toasts. *How:* batches of 20 —
the prompt lists `id: ingredients…` lines, the answer is a JSON map `{id: [diets]}`; one toast per batch; the same
`extractJSON`; stop on the first refusal. Fifteen times fewer calls; the per-recipe prompt tokens drop too. Self Test:
with `aiCall` stubbed, 45 untagged recipes make 3 calls and every recipe gets its tags.

**C5 ✓ note — The help assistant's standing instructions** (61 KB, ≈ 17,000 tokens) are sent with a cache mark
(`cache_control: ephemeral`), so repeated questions read them at a tenth of the price; each language appends its
glossary (one cache per language). They grow with every feature; at twice the size the cache write per 5-minute
window starts to show with many users. Keep an eye; a split into "always" and "on this topic" parts would be the
next step, not now.

**C6 ✓ Bounded already:** the local 30-day answer cache (300 entries) skips repeated calls; the Worker's per-household
allowances and daily/monthly ceilings; the round-up import's answer budget (2,000–16,000 tokens by page size) is
right for what it does.

**C7 ✓ Free tiers:** Firestore, Cloudflare (Workers, D1, KV, Pages), GitHub Actions (a public repository), Resend's
100 a day, Gemini's daily allowance — all watched hourly with alerts at 70 % (v38.60–v38.84); the pre-launch
measurements (20 testers at 3–40 % of each allowance) still hold.

**C9 🟡 ASK — The Self Tests run twice per release.** Every release runs the 20-minute suite on `test`, then the same
commit again on `main` (and the languages commit after it). Free, but each release waits 20 minutes longer than it
must. *How:* in `self-tests.yml` a first step asks the API for a successful "Self Tests" run with the same `head_sha`
on another branch (`gh api repos/…/actions/runs?head_sha=…&status=success`) and skips the rest when found (an
`if:` on each later step, or `exit 0` with a notice); the languages commit (`i18n/*.json` only) can be skipped
outright by a `paths-ignore`. Risk: low; the gate on main stays for anything not already green on test.
