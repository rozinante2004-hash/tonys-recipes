## 2. Findings

### Security

**S1 🔴 🟢 — Firebase API key restriction. ⚠️ needs your console.**
`index.html:144` ships `apiKey: "AIzaSy…"`. That is *normal and expected* — a Firebase web API key
is an identifier, not a secret, and your Firestore rules are what actually protect the data. But it
should still be restricted so it can't be used from anywhere else.
**Action:** Google Cloud Console → APIs & Services → Credentials → that key → Application
restrictions → **HTTP referrers** → `https://rozinante2004-hash.github.io/*`. Five minutes, no code.

**S2 🟠 🟢 — The CSP's `connect-src` allowlist is defeated by its own wildcard.**
`index.html:50` reads `connect-src 'self' https: https://lively-bread…` — the bare `https:` allows
*every* https origin, making the careful list after it decorative. Removing `https:` restores the
intent. Needs a check that nothing legitimate breaks (photo thumbnails come via `img-src`, which is
separate and already `https:` by necessity).

**S3 🟠 🟡 — Three third-party CORS proxies see every URL you import.**
`index.html:20541-20543`: `api.allorigins.win`, `corsproxy.io`, `api.codetabs.com`. These are
fallbacks behind the Worker's own `fetch-url`, but when they run they learn what you are importing,
**and they can return whatever HTML they like** — which then goes to the AI and becomes a recipe.
Low likelihood, non-trivial impact. Options: drop them entirely and let an import fail with a clear
message; or keep them but label them in the UI when used, so a weird result has an explanation.

**S4 🟠 🟡 — The Worker's app key is in the client, and the rate limiter fails open.**
`tonys-recipes-web-v1` is readable by anyone who views source (a documented, accepted trade-off).
The protection that matters is `rateLimited()` in `cloudflare-worker.js` — 40 AI calls/min/IP. Two
gaps: it **fails open** when KV is unbound or errors (`if (!kv) return null;` and the `catch`
returning `null`), and there is **no daily ceiling**, only a per-minute one. Someone who found the
key could spend your Anthropic credits steadily. Add a per-day counter and a hard monthly cap.
*This becomes important before any public release, not now.*

**S5 🟡 🟢 — No SRI on the Firebase/Google scripts** (`index.html:66-70`). They're version-pinned and
first-party Google, so risk is low, but `integrity=` costs nothing.

**S6 🟡 — `script-src 'unsafe-inline'`** is unavoidable in a single-file app with inline handlers.
Noted so it is a known trade-off rather than an oversight.

**Healthy:** `escH` / `escA` / `safeUrl` are correct and used consistently; the Firestore rules are
genuinely well thought out (the `create, update` vs `write` distinction, and the delete-is-admin-only
rule, are subtle and right); the Bring! secret is not in the repo; `object-src 'none'`,
`base-uri 'none'`, `form-action 'none'`, `frame-ancestors 'none'` are all set.

### Cost and resource use

You said you're only aware of the Anthropic cost. Here is the **complete list of things that can
cost you money or hit a quota**, and where each stands.

**C1 🔴 🟢 — The model is two generations old, and the current one is cheaper.**
`index.html:19492` pins `claude-sonnet-4-5-20250929`. Per the current price table:

| Model | Input $/1M | Output $/1M |
|---|---|---|
| `claude-sonnet-4-5` (what you run) | $3.00 | $15.00 |
| **`claude-sonnet-5`** | **$2.00** | **$10.00** |
| `claude-haiku-4-5` | $1.00 | $5.00 |
| `claude-opus-5` | $5.00 | $25.00 |

Sonnet 5 is **~33% cheaper on both input and output** *and* a newer, more capable model. The pin is
in exactly one place and flows through to the Worker, so this is a one-line change plus a test pass.
**This is the single best value-for-effort item in the whole audit.**

**C2 🟠 🟡 — Send the cheap calls to a cheap model.**
Several call sites are small classification/writing jobs that don't need a mid-tier model:
`aiCall(prompt, 80)` (diet tagging, `:27443`), `aiCall(…, 200)` (classifier, `:1170`),
`aiCall(…, 400/500)` (help assistant, `:24525`, `:24567`). On Haiku 4.5 those cost **half** of Sonnet 5
and a third of what you pay today. Needs a per-call-site model argument — currently `AI_MODEL` is global.

**C3 🟠 🟢 — The AI cache is tiny.** `AI_CACHE_MAX = 40` entries, 7-day TTL (`:19503-19504`).
Each entry is small. Raising to ~300 entries and 30 days costs a few hundred KB of localStorage and
directly removes repeat API calls. Measure the hit rate first (`_aiCacheHits` / `_aiCacheMisses`
already exist but aren't surfaced).

**C4 🟠 🟡 — No prompt caching on the big system prompt.** `HELP_SYSTEM_PROMPT` is long and resent in
full on every help question (`:24525`). Anthropic prompt caching (`cache_control`) would cut the
input cost of repeat help/suggest calls substantially. Requires passing the system prompt as a
proper `system` block rather than concatenating it into the user turn — which is the better shape anyway.

**C5 🟠 🟡 — Cloudflare KV: one write per request, against a 1,000/day free limit.**
`rateLimited()` does `kv.put(...)` on **every allowed request**. Cloudflare's free tier allows
**1,000 KV writes/day**. Ordinary family use won't reach it, but one "Auto-fetch missing photos"
across 300 recipes, or a round-up import that fetches 10 pages, burns through dozens to hundreds in
a burst. When the limit is hit the `put` throws, is caught, and **the rate limiter silently stops
limiting**. Fix: sample the writes (e.g. write 1-in-5 and multiply), or move the counter to the
Cache API / a Durable Object.

**C6 🟢 — Firebase (Spark, free): comfortable.** Each full load reads roughly one doc per recipe plus
`meta` plus photo docs. At 300 recipes that's ~600 reads/load against a **50,000 reads/day** free
quota — you'd need ~80 full loads a day to notice. Storage: photos are ≤60 KB each in their own docs,
so 300 photos ≈ 18 MB against 1 GB. No action.

**C7 🟢 — Photo search APIs (Pixabay / Pexels / Unsplash): free tiers, generous, per-request.**
Only consumed when you press "Search web for photo" or auto-fetch. No action, but see C5 — auto-fetch
is the burst that matters for KV.

**C8 🟢 — GitHub Pages and Cloudflare Workers requests: free at any plausible volume here.**
Workers free tier is 100,000 requests/day.

**⚠️ needs your console:** your actual Anthropic spend is only visible at
console.anthropic.com → Usage. Worth a look before and after C1, so the saving is a measured fact
rather than my arithmetic.

### Performance

**P1 🟠 🟡 — 36% of what every device downloads is the test suite.**
590 KB of the 1.63 MB payload is `SELF_TESTS`. It is *excellent* that the tests exist and I would not
shrink them — but they don't need to ship to your phone. Moving them to `tests/self-tests.js`, loaded
on demand when you open ⚙️ → 🧪 Self Test, would cut the download and the parse time by about a third.
The runner and CI would load that file directly. **The catch:** it breaks the single-file property the
project deliberately has. Worth discussing before doing — it's the one item here that trades away a
stated design principle.

**P2 🟡 🟢 — `renderFilters()` is the slow half of a re-render** (170 ms vs 88 ms at 1000 recipes)
because it recomputes `oneAwayCount()` and the no-photo count over the whole library on every call.
At 300 recipes it's ~50 ms — not a problem, but it's called on every filter toggle. Memoise both counts.

**P3 🟢 — Rendering is fine at your ceiling.** No virtualisation needed at 100–300 recipes. Revisit
only if the library goes past ~1000.

### Functionality and data safety

**F1 🟡 🟢 — Dead export:** `window.sendToBring` is assigned and never referenced anywhere else.

**F2 🟠 🟢 — Backups are manual.** `checkBackupOverdue()` shows a toast, but nothing writes a backup
automatically. Your recipe data survives in Firestore, but the clip incident showed the gap: when
something is deleted from *both* the list and the cloud, the only recovery is a file you remembered
to save. Consider an automatic monthly export to the Downloads folder, or at least escalating the
reminder when the last backup is very old.

**F3 🟠 🟡 — Restore is all-or-nothing.** `backupRestoreFile()` replaces everything with no merge
option, which is why recovering your clip meant reading the JSON by hand. A "restore only the
recipes missing from my library" mode would have made that a two-tap fix.

**F4 🟡 🟡 — No undo for a destructive import.** Deleting has undo; `collectSelectedInto` now refuses
to lose a recipe (v36.11); but "Update existing" on an import overwrites with only version history
as a fallback, and that's per-recipe.

### UI / UX and accessibility

**U1 🟠 🟡 — A third of the phone screen is fixed chrome.** Measured: 202 px header + 85 px filter bar
= **34% of a 390×844 screen**, before a single recipe. Collapsing the header on scroll (leaving the
search field and the filter bar pinned) would give back ~150 px. This is the biggest visual
improvement available on the phone.

**U2 🟡 🟢 — `<html lang="en">`** on an app whose content is substantially Hebrew. Affects screen
reader pronunciation and hyphenation. Per-element `dir="auto"` is already done well; the page-level
`lang` is the gap.

**U3 🟡 🟡 — Accessibility beyond contrast is unaudited.** 303 buttons, 38 `aria-label`s, 12 `role=`
attributes, 9 `tabindex`. `labelIconButtons()` handles the icon-only ✕/heart buttons, and most other
buttons carry visible text, so this is likely better than the raw ratio suggests — but focus order,
focus trapping in modals, and a screen-reader pass have not been checked. Out of scope for one audit;
worth its own session if public release gets close.

**U4 🟡 🟢 — The Select frame costs a whole filter row on phones** (v36.10 trade-off, documented).
Revisit if the filter bar ever gets rearranged.

## 5. Suggestions beyond fixing things

1. **Surface the AI cache hit rate** in ⚙️ → Sync Health. `_aiCacheHits` / `_aiCacheMisses` already
   exist; showing them turns C3 from a guess into a measurement.
2. **A cost line in Sync Health** — count AI calls this month locally. Not billing-accurate, but it
   makes spend visible where you'd notice it.
3. **Ingredient normalisation** — "2 onions" and "onions, 2" are different strings today, which
   affects the pantry, "one item away", and Bring!. A canonical-name pass would improve three
   features at once.
4. **A "cook this week" plan** — you have cook history, favourites and the pantry; a weekly plan view
   is a natural next feature rather than a fix.
5. **Bulk edit** — Select mode can already delete, share and collect; adding "set category" or
   "add diet tag" to that bar would save a lot of tapping at 300 recipes.
6. **Export a collection as one document** — the Word export is per-recipe or all-recipes; a
   collection is the natural middle unit now that collections are first-class.

## 6. Checked and found sound

Worth recording, so a future pass doesn't re-litigate these:

- **No TODO / FIXME / HACK markers anywhere.** Unusual and good.
- **Escaping is correct and consistent** — `escH` for text, `escA` for attributes, `safeUrl` for
  hrefs, with the reasoning written down.
- **Firestore rules** — the `create, update` vs `write` distinction and admin-only delete are
  correct and subtle; the consequence for write-role members is documented rather than hidden.
- **Photo storage architecture** — IndexedDB locally, one Firestore doc per photo, recipes doc kept
  photo-free, `originalPhoto` never synced, backups inline the bytes so they stay self-contained.
  This is the right design and it is well defended by tests.
- **Service worker** — app-shell-only caching with an explicit file list, `version.json` never
  cached, and the catch-all bug from an earlier version documented at the point where it was fixed.
- **Deletion propagation** — explicit, never inferred from a cloud diff. This is what made the clip
  recoverable from another device.
- **CI** — syntax check, 234 self-tests, five-string version guard, Worker checks, and now a
  two-theme contrast scan. Every step can actually fail (I verified the new one by reintroducing the
  bug it catches).
- **1.63 MB is served once and cached.** The size matters for first load and for each version
  update, not for daily use.
