# Audit — 3 November 2026 (v39.24 → v39.25)

Tony, 3 Nov: "let's run another audit, focusing on usability, functionality, efficiency and visuality" — "Also, please
make sure all the self test tests are indeed testing what they are supposed to test." — "Once you are done with the
audit, please prepare an execution plan, ordered from most severe to least severe, and immediately start executing
everything you consider needs fixing. Items that require inputs or decisions from me, leave to the end."

## How it was checked

- **Every Self Test against its own code** (new: `tests/selftest-knockout.js`). Each of the 429 tests that run without
  the network was run as usual, then again with each app function it calls replaced by one that does nothing, one at
  a time; a test that still passed with every one of them gone could not catch a fault. Every "passed anyway" was run
  again in a fresh page (one knock-out can leave the page changed for the next), and a crash in a test's own set-up
  was told apart from the test's own assertion failing. A second pass (`--subject`) matched each test's NAME to the app
  functions it names ("crud_fav" → `toggleFav`) and knocked those out. Tests that reach the app through a browser event
  or through the owner's page (manage.js) were checked by editing the app by hand and running them.
- **A walk of 27 screens** — the main screen, a recipe (English, Hebrew, a collection), the editor, every menu,
  Help, Family Access, Share, the identifier, Sync Health, About, the pantry, the converter, the imports, Explore —
  with a signed-in kitchen and real-looking recipes, on a phone (390 px) in light and dark, and on a computer
  (1280 px). Screenshots looked at side by side; the page's errors collected (none from the app — only the blocked
  network of the test machine).
- **On a phone, measured**: tap targets and text sizes on the main screen and six windows; windows at 320, 390 and
  390 zoomed in (v39.24).
- **Speed on a phone's processor** (4× slower than the test machine) with 150 and 600 recipes: drawing the grid,
  searching, opening a recipe, a filter, the filter bar.
- **What a first visit downloads**: the beta's built page.

## Found and fixed (v39.25)

### 1. Self Tests that test what they say

332 of 429 tests failed on their own assertions with their code knocked out; 92 did not. Read one by one:

- **Rewritten to exercise the real code** (each then shown to fail with it knocked out, with a plain message):
  - `fn_render` "renderGrid() works" — passed with renderGrid doing nothing: the grid was already full from before.
    Now the grid is emptied, a probe recipe drawn, its card and name checked.
  - `fn_filters` "Filter functions work" — only checked that four functions existed. Now ❤️ Favourites must hide a
    non-favourite and bring it back, and Clear filters must clear them all.
  - `crud_save` "Save & delete test recipe" — never looked at what was saved. Now the recipe must be on the device
    after saving and gone after deleting.
  - `crud_fav` "Favourite toggle works" — flipped the flag by hand. Now the card's ❤️ (`toggleFav`) must make a
    favourite, stamp it (so it syncs), save it, and a second ❤️ take it back.
  - `perf_search_debounce` "Search input is debounced" — checked the wiring, never the waiting. Now typing five
    letters must not redraw the grid, and a pause must redraw it once.
  - `feat_refresh_foreground` "Cloud re-checks when app returns to foreground" — only checked that a variable existed.
    Now coming back to the app must read the cloud once, and not again within 20 s (shown by editing the app: without
    the read, and without the 20-second limit, it fails).
  - `safety_orphan_sweep` — read the function's text. Now it sweeps: an orphaned photo goes, a live recipe's never.
  - `export_bulk` "Bulk export of selected recipes works" — checked that functions existed. Now two of three selected
    recipes are exported and exactly those two must be in the document.
  - `select_bar_compact` — measured CSS with the bar never open. Now select mode must show it, count and Cancel on
    one line, and Cancel put it away.
  - `ui_owner_contrast` "… in BOTH themes" — with the theme switch broken it measured one theme twice. Now each switch
    must change the page.
  - `data_normalize`, `feat_cat_skills` — "must not throw" also passed with nothing drawn. Now the card (and the
    filter bar's Skills & Methods) must be drawn afresh.
  - `safe_restore_confirms` "Restore asks before replacing everything" — read the function's text. Now a backup file
    is restored: the question must come, say that replacing cannot be undone, and Cancel must change nothing.
- **Made deterministic**: `ai_model_routing`, `ai_system_is_its_own_block`, `ai_our_own_refusal_is_final` counted
  every request — the app's own background ones too, so on a fresh page they failed now and then. They count only
  the AI's requests now. (`farm_visitors` and `ux_signin_always_reachable` take longer than the checker allowed;
  with a longer limit both catch their faults.)
- **Checked and fine as they are**:
  - ~38 tests "only crash" when their function returns nothing (e.g. `wa_parse` reads the result of `waParse`) — a
    crash is a failure; their assertions check the results.
  - ~15 deliberate checks of the page's own text or structure (`sec_csp_present`, `log_kinds_are_real`,
    `ai_calls_prove_who`, `brand_in_the_page_itself`, `sw_serves_only_the_app_shell`, …) — they say so.
  - ~23 "is there" checks whose names say so ("Backup functions defined", "Camera import function exists", …):
    shallow, honest; the behaviour behind most of them has its own tests.
  - The two Feedback tests depend on the owner's page: shown by breaking 📋 Copy reports in manage.js — the test fails.

### 2. The backup reminder (functionality, usability, visuality)

A kitchen never backed up (every new tester) was told "💾 No backup has been taken yet" at **every** opening, for 12 s,
**over whatever had just been opened** — on a phone it hid an open recipe's buttons — and on a phone its words stood
**one to a line** beside the button (a notice centred with `left: 50%` is laid out in half the screen). The reminder
meant to stay after 60 days went away after 9 s (`duration || 9000` turned 0 into 9000).
Now: a notice is as wide as its words, up to the screen; the 60-day one stays until dismissed; the reminder comes
once a day at most (as the 90-day dialog already did) and waits until no window is open. Self Test
`backup_reminder_considerate` (fails on the old code); tests/phone-fit.js checks the notice's words at 320 and 390 px
(on the old code: 46–51 px wide).

### 3. Phones: tap targets and small text (usability, visuality)

Measured at 390 px: the header's round buttons 28 px, a card's ❤️ 24, a recipe's tick boxes 22, scale and filter
chips 26–28, Family Access's buttons 24 (a finger needs ~44); text at 10–11 px in labels, pills, the recipe window's
controls and nearly all of Family Access. On a touch screen now: each small button keeps its look and gets an
invisible margin that takes the tap (8 px above and below for the round buttons, ❤️ and tick boxes; 5 px for chips in
rows, so two rows never overlap); text is at least 12 px (the uppercase category badges 11). Text under 12 px: Family
Access 19 → 3 places, the recipe 12 → 3, the editor 8 → 1. tests/phone-fit.js checks that a tap 6 px above ⚙️ and a
card's ❤️ lands on them.

### 4. Speed with a large collection (efficiency)

On a phone's speed, with 600 recipes: a category tap 410 ms, redrawing the filter bar 423 ms, drawing the grid 150 ms —
mostly the browser laying out all 600 cards when a screen shows a dozen. Cards off the screen are now laid out only
when they come near (`content-visibility: auto`, a card's usual height meanwhile). After: 85 ms, 40 ms, ~100 ms.
(150 recipes: a category tap ~100 ms before. The biggest kitchen today has 66.)

## Checked and fine

- No error from the app on any of the 27 screens, in either theme or on the computer.
- Dark mode: every screen walked reads well; no light panel left behind.
- Windows open inside the screen at 320, 390 and zoomed (v39.24); the long-name header wraps.
- The same in the Hebrew interface (320 and 390 px) and with a phone held sideways (844 × 391); the sign-in screen fits
  320 px and scrolls.
- Every CI scan passes on v39.25 locally: contrast in both themes, accessibility (axe, the page and 33 dialogs: no
  serious or critical finding), the phone's screen budget, every ✕ in view (56 checks), double-clicks, the Worker.
- Searching and opening a recipe stay quick at 600 recipes (search ~100–130 ms after the pause, a recipe < 20 ms).
- Repeating timers already slow down when the app is idle (v38.54).
- The share window, the identifier, Sync Health, About and the pantry fit and read well on a phone.

## Watch

- `content-visibility` is new to Safari 18 (iOS 18). On older iPhones nothing changes; on newer ones the grid should
  scroll without jumps (each card keeps the height it was last seen at).
- tests/selftest-knockout.js takes ~15 minutes; worth running before a large change to the suite.

## Needs Tony (last)

1. **"⇅ Imp/Exp ▾"** — it repeats three items of "+ Add Recipe ▾" (🔗 From URL, ✍️ Free-hand text, 📷 Scan), and its name
   is jargon. Proposal: call it **"📁 Files & backup ▾"** and keep what only it has — 📁 From File, 📂 Drop File Here,
   📄 All to Word, 💾 Backup — Save, 📂 Backup — Restore; adding from a link, text or a photo stays in "+ Add Recipe".
   (Mock-up: the menu as it is, and as proposed.) Say yes, or keep it as it is.
2. **"··· More"** — fourteen items in one list. Proposal: the same items under five small headings — *Ideas* (Explore,
   Suggest, What can I make), *Tools* (Converter), *Kitchens and people* (Connect, Chat with family, Chats with
   linked kitchens, Sent to me, I sent, Share this app), *WhatsApp* (Ask my groups, Recipes in my chats), *Tidy up*
   (Auto-tag diet types, Auto-fetch missing photos). (Mock-up: as it is, and as proposed.) Say yes, or keep it.
3. **A first visit's 1.8 MB** — after it, the app is kept on the device. Splitting the rarely used parts (WhatsApp
   import, the translation tools) into files fetched when first opened could save about a third; a few days' work and
   some risk. Recommendation: not now — revisit if testers on slow connections say the first opening is slow.
