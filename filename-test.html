🍴 Filename Test

The question: is the local Python Save Helper still needed, or does plain Chrome on your Ubuntu box already keep Hebrew / Russian filenames intact? Test 1 decides it. This page saves nothing and changes nothing in the app.

What actually decides this: your desktop's locale

Chromium sanitises download filenames against the character encoding of the process locale, not the page's. Launched under a non-UTF-8 locale (LANG empty, or C/POSIX) it throws away every non-ASCII character in the name and falls back to Download — which is exactly the symptom that made us write the helper. Launched under a UTF-8 locale the same Chromium build keeps עוגת שוקולד של סבתא.docx byte for byte, through the app's own export code, with the helper switched off. So this is not a Chrome limitation and not something the app can fix in JavaScript — it is one environment variable on the machine doing the downloading.
Run this in a terminal on the same machine:
locale
If LC_CTYPE reads en_GB.UTF-8 (or any .UTF-8), that shell is fine. If it reads POSIX or C, that is the bug — and the fix is the locale, not the helper.
But your terminal is not what matters — Chrome's own environment is. A browser started from a desktop launcher inherits the graphical session's environment, which can differ from a terminal's. This reads it straight out of the running process: 
pid=$(pgrep -o -f 'chrome|chromium')
tr '\0' '\n' < /proc/$pid/environ | grep -E '^(LANG|LC_|GDM_LANG|LANGUAGE)=' || echo "(nothing set — that is the bug)"
That is the authoritative reading. Empty output, or LANG=C / LANG=POSIX, explains a test 1 failure completely.

Every test below downloads a small .docx-ish file using this name.

1. Classic browser download the deciding test

<a download="…"> + blob URL — exactly what the app does when the Python helper is switched off. In the lab this keeps the name perfectly under a UTF-8 locale and destroys it under POSIX. Only your machine can say which one you have.
If this passes, the helper is not required and can be retired.
Not run yet.

2. File System Access API auto-verified

showSaveFilePicker({suggestedName}) — opens a real Save dialog. The browser tells us the filename it actually used, so this one verifies itself. (Chrome only, needs https.)
This is the natural replacement if test 1 fails: no background process, no upload, and it is self-verifying. The cost is that every export pops a Save dialog instead of dropping straight into Downloads, and it does not exist on iOS Safari — so the app would need to keep the plain <a download> path anyway for the phone.
Not run yet.

3. Cloudflare Worker download manual check

Uploads the file to your Worker, which serves it back with Content-Disposition: attachment; filename*=UTF-8''… — the standards-compliant way to send a non-ASCII filename. Your Worker already supports this; the app doesn't use it yet.
⚠️ Only a fallback of last resort. Routing real exports this way would send every backup — recipes and photos — through Cloudflare purely to fix a filename. Worth knowing it works; not worth adopting unless tests 1 and 2 both fail.
Note the same locale caveat applies: under a non-UTF-8 locale Chromium mangles a Content-Disposition name just as thoroughly as an <a download> one, so a failure here is evidence about the locale, not about the Worker.
Not run yet.

The current primary method. The helper replies with the exact path it wrote, so this verifies itself. Only works if the helper is running on this machine.
